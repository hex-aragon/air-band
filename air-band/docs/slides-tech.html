스틱을 휘두르면 브라우저에서 드럼 소리가 나는 에어 밴드. 오늘은 그 1단계 결과를 공유합니다.

01무엇을 만드나

🥢 휘두르면

손목이나 스틱에 단 작은 보드가 타격 동작을 감지합니다.

📡 BLE로 보내고

"언제, 어떤 드럼을, 얼마나 세게"만 8바이트로 전송합니다.

🔊 브라우저가 연주

앱 설치 없이 주소 하나로 엽니다. PC Chrome/Edge, Android Chrome.

최종 목표: 동작만으로 스네어 / 하이햇 / 탐을 구분하는 양손 에어 드럼 (TinyML)

02전체 구조

보드는 판단만, 소리는 브라우저가 냅니다. 버튼과 IMU는 같은 전송 경로를 씁니다.

038바이트 타격 패킷

  • Nordic UART Service (NUS) notify
  • 광고 이름 AirBand-R
  • 연결 간격 7.5~15ms 요청
  • 한 notify에 여러 패킷이 붙어 와도 8바이트 단위로 자름
바이트필드값
0손0 = 오른손
1모드0 = 드럼
2드럼 종류0 스네어 · 1 킥 · 2 하이햇 · 3 탐
3세기1~127 (MIDI velocity)
4~7보드 시각millis() LE uint32

04펌웨어: 흔들림 → 타격

  • 100Hz 샘플링 (micros() 비교)
  • 3축 가속도 크기(g)의 국소 최대값
  • 임계값 2.5g 이상 + 불응기 60ms
  • 세기: 2.5g → 1, 12g → 127
  • classifyHit() 훅 → 2단계 TinyML 자리

지연 포인트: 전송 분리

Bluefruit notify는 송신 버퍼가 차면 최대 100ms 대기합니다. 샘플링 루프는 FreeRTOS 큐에 대기 0으로 넣기만 하고, 별도 태스크가 전송합니다.


static void emitHit(uint8_t cls, uint8_t vel, uint32_t ts) {
  HitPacket p;
  buildPacket(p, cls, vel, ts);
  xQueueSend(g_hitQueue, &p, 0);   // 대기 0: 큐가 가득 차도 막히지 않음
}

05그런데… 센서가 없었다


[I2C] scan: 0x6A
[IMU] 감지 실패 — 배선/주소/모델 확인 후 재시도
[IMU] 0x6A reg0x0F=FF reg0x75=FF reg0x00=61
  • 0x6A는 IMU가 아닌 보드의 전원 관리 칩
  • NU40 DK에는 IMU가 없음 → 외부 모듈 필요
  • 펌웨어가 IMU를 기다리느라 BLE 광고도 안 함

💡 덤: LSM6DS 계열 IMU는 기본 주소가 0x6A라 이 보드에서는 SA0 → 3V3 (0x6B)로 써야 충돌이 없습니다.

센서만 빼고 나머지 경로 전체를 먼저 검증합니다.

킥버튼 2 · 키 2
하이햇버튼 3 · 키 3
탐버튼 4 · 키 4

[IMU] 없음 — 버튼 전용 모드로 동작
[BTN] 버튼 1~4 → 드럼 0~3
[BLE] 광고 시작: AirBand-R

07웹앱

드럼마다 위치·색이 다른 물결 · 누른 패드가 빛남 · 입력 출처(보드/화면) 로그

08받자마자 소리 내기

  • 시작할 때 드럼 4개를 모두 AudioBuffer로 준비
  • 타격 오면 start()만 호출 (fetch·디코딩 없음)
  • wav가 없으면 코드로 합성 → 에셋 없이 동작
  • 세기 → 볼륨: (v/127)^1.6 곡선
드럼합성
스네어220→160Hz 사인 + 고역 노이즈
킥150→45Hz 급하강 사인 + 클릭
하이햇5kHz 이상 노이즈, 0.12초
탐180→110Hz 사인 + 약한 노이즈
